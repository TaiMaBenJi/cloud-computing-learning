第 14 章 · 监控与日志（给系统装"体检仪"和"行车记录仪"）

服务器不会打电话告诉你它不舒服。监控 = 体检仪（当前状态如何）；日志 = 行车记录仪（刚才发生了什么）。
韩国赛第 3 任务、2026 全锦赛 task1 都有完整的监控栈评分点（Prometheus + Grafana + 日志管道）。这是"运维"变"高薪运维"的分界线。
预计学习时间：2-3 周。

14.1 监控三大支柱（先建立全景）

支柱回答什么问题工具代表
指标（Metrics）"现在怎么样？"（数字化的状态）Prometheus、CloudWatch
日志（Logs）"刚才发生了什么？"（事件的文字记录）ELK、Loki、journald
追踪（Traces）"这一个请求都经过了哪？"（跨服务链路）Jaeger、OpenTelemetry

新手先精通前两个，追踪等有微服务架构再学。

监控什么？记两个方法论

  • USE（对机器）：Utilization（利用率）、Saturation（饱和度）、Errors（错误）——看 CPU/内存/磁盘/网络是否吃满
  • RED（对服务）：Rate（请求率）、Errors（错误率）、Duration（延迟）——看服务是否健康

14.2 Prometheus：指标监控当家花旦

14.2.1 原理（30 秒版）

Prometheus 主动去"抓"（pull） 各个目标暴露的指标（不像传统监控等目标上报）。每个目标上跑一个"信息页"（/metrics），Prometheus 每隔 15 秒抓一次，存进自己的时间序列数据库。

[被监控机器] node_exporter → /metrics（一堆数字）
        ▲ 每15秒抓一次
[Prometheus 服务器] ← 存储 + 查询（PromQL）+ 告警规则
        ▲ 读数据画图
[Grafana] → 漂亮的仪表盘
        │ 触发告警
[Alertmanager] → 发邮件/钉钉

14.2.2 实战安装（单机练习环境）

# ① 要监控的机器上装"暴露指标的小程序" node_exporter
wget https://github.com/prometheus/node_exporter/releases/download/v1.8.2/node_exporter-1.8.2.linux-amd64.tar.gz
tar xzf node_exporter-*.tar.gz
sudo mv node_exporter-*/node_exporter /usr/local/bin/
# 做成 systemd 服务（回忆第 3 章）
sudo tee /etc/systemd/system/node_exporter.service > /dev/null <<'EOF'
[Unit]
Description=Node Exporter
[Service]
ExecStart=/usr/local/bin/node_exporter
Restart=always
[Install]
WantedBy=multi-user.target
EOF
sudo systemctl daemon-reload && sudo systemctl enable --now node_exporter

# 验证：能看到一堆指标就成功
curl -s http://localhost:9100/metrics | head -20
# ② 安装 Prometheus 本体（假设同一台机器）
wget https://github.com/prometheus/prometheus/releases/download/v2.53.0/prometheus-2.53.0.linux-amd64.tar.gz
tar xzf prometheus-*.tar.gz && cd prometheus-*
# 改配置：告诉它去哪里抓指标
cat > prometheus.yml <<'EOF'
global:
  scrape_interval: 15s        # 每 15 秒抓一次

scrape_configs:
  - job_name: 'node'          # 任务名
    static_configs:
      - targets: ['localhost:9100']    # 抓本机的 node_exporter
EOF
# 启动（练习直接跑；生产同样做成 systemd）
./prometheus --config.file=prometheus.yml &

打开浏览器访问 http://服务器IP:9090 —— Prometheus 的 Web 界面：

  • 搜索框输入 node_cpu_seconds_total → 点 Execute → Graph → 能看到 CPU 曲线！
  • 这就是你第一次"看到"服务器的运行状态。

14.2.3 PromQL 四板斧（够用了）

# ① 当前 CPU 使用率（%）
100 - (avg by(instance) (rate(node_cpu_seconds_total{mode="idle"}[5m])) * 100)

# ② 内存使用率
(1 - node_memory_MemAvailable_bytes / node_memory_MemTotal_bytes) * 100

# ③ 磁盘使用率（根分区）
(1 - node_filesystem_avail_bytes{mountpoint="/"} / node_filesystem_size_bytes{mountpoint="/"}) * 100

# ④ 最近 5 分钟平均负载
node_load5

心法：rate(...[5m]) = "5 分钟内的每秒变化率"（对付只增不减的计数器）；by(instance) = 按机器分组。这两招覆盖 70% 的场景。

14.2.4 告警规则（从"看"到"管"）

建 alerts.yml：

groups:
  - name: basic-alerts
    rules:
      - alert: HighCPU            # 告警名
        expr: 100 - (avg by(instance)(rate(node_cpu_seconds_total{mode="idle"}[5m])) * 100) > 80
        for: 5m                   # 持续 5 分钟才告警（防抖动）
        labels:
          severity: warning
        annotations:
          summary: "CPU 高: {{ $labels.instance }}"    # 告警内容模板

prometheus.yml 里挂上 rule_files: [alerts.yml]，重启生效。比赛里"配置 HighLatency 告警规则"这类评分点，就是这个东西（韩国 2026 题的原题）。

14.3 Grafana：把数字画成"仪表盘"

Prometheus 的界面太朴素，Grafana 是专业"仪表盘"。

# 安装（官方源）
sudo apt install -y apt-transport-https software-properties-common
wget -q -O - https://apt.grafana.com/gpg.key | sudo apt-key add -
echo "deb https://apt.grafana.com stable main" | sudo tee /etc/apt/sources.list.d/grafana.list
sudo apt update && sudo apt install -y grafana
sudo systemctl enable --now grafana-server

打开 http://服务器IP:3000（默认账号密码都是 admin，首次登录改密码）。

三步出图：

  1. 加数据源：Configuration → Data Sources → Add → Prometheus → URL 填 http://localhost:9090 → Save & Test（出现绿色 "Data source is working"）
  2. 建仪表盘：Create → Dashboard → Add visualization → 选 Prometheus
  3. 粘一条 PromQL（比如上面的 CPU 公式）→ 出图！右上角保存。

进阶：直接用现成模板（偷懒最快路径）：Dashboard → Import → 输入 ID 1860（Node Exporter Full，社区最火的服务器监控盘）→ 选数据源 → 立刻得到几十张专业图表。你的服务器监控在 10 分钟内达到了专业水平。

14.4 日志：让每台机器"写日记"

14.4.1 本机日志先看明白

journalctl -u nginx --since "1 hour ago"     # 某服务的日志
journalctl -p err -b                         # 本次开机以来所有 error
journalctl -f                                # 实时跟踪（等于 tail -f）
journalctl --disk-usage                      # 日志占了多少磁盘（记得清理）
journalctl --vacuum-size=500M                # 磁盘紧张时的救命命令

传统文本日志在 /var/log/（你早就熟悉了）：syslog、auth.log、nginx/…

14.4.2 日志为什么需要"收集"？（概念）

10 台机器，每台都有日志——排障时要一台台登进去翻？ 不行。所以要把日志集中收集：

各机器上的采集器(Fluent Bit) → 中心存储(OpenSearch/Loki/CloudWatch) → 统一搜索

韩国赛的评分点："把应用日志送进 OpenSearch，建 index pattern 叫 app-log"——就是这条管道。

14.4.3 Fluent Bit 实战（轻量采集器，云原生标配）

curl https://raw.githubusercontent.com/fluent/fluent-bit/master/install.sh | sh

配置 /etc/fluent-bit/fluent-bit.conf：

[INPUT]
    Name              tail
    Path              /var/log/nginx/access.log
    Tag               nginx.access

[OUTPUT]
    Name              stdout        # 练习先输出到屏幕；生产改成转发到 ES/CloudWatch
    Match             *
sudo systemctl restart fluent-bit
tail -f /var/log/syslog | grep fluent    # 看到采集器在吐日志 = 管道通了

14.4.4 云上版本：CloudWatch Logs（AWS 场景）

# EC2 上装 CloudWatch Agent（控制台里有向导），把 syslog/应用日志推上去
# 然后就能在 AWS 控制台 → CloudWatch → 日志组 里统一搜索
# "Logs Insights" 查询示例：
# fields @timestamp, @message | filter @message like /ERROR/ | sort @timestamp desc | limit 50

记住这个界面：比赛里排查线上问题、评分系统查日志，都在这里。

14.5 综合实战：给第 12 章的云架构加监控

任务清单（韩国赛 task 的迷你版）：

  1. 给两台 Web 服务器装 node_exporter
  2. 一台专用"监控机"装 Prometheus + Grafana
  3. Prometheus 抓取两台 Web 服务器的指标（targets 填两台 IP）
  4. Grafana 导入 1860 模板，看到两台机器的图表
  5. 配置 2 条告警：CPU>80% 持续 5 分钟、磁盘>85%
  6. 用压测工具（第 8 章学的 ab/stress）让 CPU 冲高，观察告警从 Pending → Firing
  7. 把 nginx 日志用 Fluent Bit 收集到一处（练习即可）
  8. 画一张监控架构图贴到你的笔记本
