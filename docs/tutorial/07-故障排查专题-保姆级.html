第 7 章 · 故障排查专题（从"瞎猜"到"破案"）

本章不教新软件，教能力：系统坏了，怎么一层层找出原因。
这是运维人员最值钱的技能，也是世界赛 Module D（排障模块）的直接对应——那个模块就是给你一台"坏掉的系统"，限时修好。
预计学习时间：2 周（反复回来翻）。

7.1 排障心法（先背下来，受益终身）

三条铁律

  1. 先看现象，再猜原因。 不要一上来就"重启试试"。重启能让问题消失，但能让它下周再来。
  2. 从下往上，逐层排除。 网络问题就从网卡→IP→网关→端口→服务一层层验（第 2 章的四层法）。服务问题就从头到尾：进程在吗→端口在听吗→配置对吗→日志说什么。
  3. 相信日志，不要相信直觉。 你说"应该是 xx 问题"，日志说"不是"。日志赢。

标准破案流程（六步）

① 收集现象：谁？什么时间？什么操作？看到什么错误？（现象越具体越好）
② 缩小范围：是一个人用不了，还是所有人都用不了？（关键分岔口）
③ 逐层验证：从底层往上层，每层用命令"验尸"
④ 形成假设：基于证据提出"最可能的原因"（1-2 个，不许猜 10 个）
⑤ 验证假设：用最小代价的实验证明/否定它（改一个变量，看结果）
⑥ 修复 + 复盘：修好后确认正常，记录"原因+解决方案"到自己的笔记本
"一个人用不了 vs 所有人用不了"是全宇宙最有用的分岔问题。 一个人 → 大概率是客户端/权限问题；所有人 → 服务器/网络问题。

7.3 实战案例库（18 个案例，每个都是真实剧本）

用法：先看"现象"，合上答案自己想想怎么查；再看排查思路。做多了会有肌肉记忆——这就是排障的"题海战术"。

案例 1：网站打不开（Connection refused）

现象：curl: (7) Failed to connect to xxx port 80: Connection refused 思路：连接拒绝 = "门都不开"（服务没在听）。

sudo systemctl status nginx        # ① 服务活着吗？→ 发现 inactive (dead)
sudo journalctl -u nginx | tail -30 # ② 为什么死？→ 日志说 "bind() to 0.0.0.0:80 failed"
ss -tlnp | grep :80                # ③ 80端口被谁占了？→ apache2 占着！
sudo systemctl stop apache2        # ④ 元凶找到
sudo systemctl start nginx         # ⑤ 修复
curl localhost && echo OK          # ⑥ 验证

根因：两个 Web 服务器抢 80 端口。教训：一台机器上同类服务只能有一个占同一个端口。

案例 2：网站超时（Timeout）——"能连上但没响应"

现象：curl: (28) Connection timed out（注意和 cases 1 的区别） 思维分岔：Connection refused = 门没开；Timeout = 门开了但人不见了/路被挡。

curl -v http://目标                  # 看卡在哪一步
# 卡在 "Trying 1.2.3.4..." → 网络层不通（路由/防火墙 DROP）
# 连上了但等响应超时 → 服务卡死
# ① 网络层：ping 目标、traceroute 目标
# ② 防火墙：iptables -L -n 看是不是 DROP
# ③ 服务层：如果连上了，看服务有没有卡（top 看 CPU/内存，看线程数）

常见根因：防火墙 DROP 规则、后端服务死锁、数据库慢查询堵住请求。

案例 3：服务器磁盘满了（头号杀手）

现象：网站莫名其妙报错、服务起不来、No space left on device

df -h                          # ① 哪个分区满了？（通常是 / 或 /var）
du -sh /var/* 2>/dev/null | sort -rh | head -10   # ② /var 里谁最大？
# 常见元凶：/var/log 日志、/var/lib/docker、应用写的日志
# ③ 精准定位到文件：
du -ah /var | sort -rh | head -20

解决方案：

# 临时：清掉旧日志（确认后再删！）
sudo journalctl --vacuum-size=200M        # journal 日志只留 200M
sudo rm /var/log/some-app/old.log.*       # 删除具体的历史日志
# 根治：配 logrotate（日志自动切割和清理）
sudo nano /etc/logrotate.d/myapp
/var/log/myapp/*.log {
    daily            # 每天切一次
    rotate 7         # 保留 7 个
    compress         # 老的压缩
    missingok
}

比赛提醒：世界赛排障模块里"磁盘满"是经典埋伏点，df -h 要成为你的条件反射。

案例 4：内存不够（OOM Killer 杀进程）

现象：某个服务莫名其妙消失，日志里什么都没有。

dmesg | grep -i "killed process"    # 内核日志里找 "Out of memory"
free -h                              # 看看内存状况

根因：Linux 内核有个"OOM Killer"，内存耗尽时它会"选择性杀人"（通常杀内存占用最大的）。你的服务就是被杀的那个。 解决：找出真凶（top 按 M 排序看谁大）；加内存；限制服务内存；加 swap 应急（swapon，但性能会降）。

案例 5：CPU 100% 怎么查

top                      # ① 看是哪个进程
top -H -p 12345          # ② 如果是多线程程序，看哪个线程
# ③ 如果是 java/python，用火焰图级别工具：perf top
sudo perf top            # 看哪个函数在烧 CPU
# ④ 常见原因：死循环 bug、挖矿病毒（！）、流量激增、正则回溯

安全警报：服务器 CPU 100% 且你没跑什么任务 → 优先怀疑被入侵挖矿：top 看陌生进程名（xmrig、kdevtmpfsi 之类），查 crontab -l 有没有陌生定时任务，查 /tmp 有没有可疑文件。这是新手站长最常见的"被黑"姿势。

案例 6：服务启动失败（systemd failed）

sudo systemctl status 服务名       # ① 看红字提示
sudo journalctl -u 服务名 -n 50    # ② 看详细日志
# 万能排查顺序：
# a) 配置文件语法（每个软件有自己的检查命令：nginx -t / named-checkconf / sshd -t）
# b) 端口冲突（ss -tlnp）
# c) 权限问题（服务以 www-data 运行，文件却是 root 的？）
# d) 依赖服务没起（数据库没起，应用起不来）
# e) 磁盘满 / 内存不足（回家看案例 3、4）

案例 7：端口被占用（Address already in use）

sudo ss -tlnp | grep :8080          # 谁占着？
sudo lsof -i :8080                   # 同上（更详细）
# 要么停掉旧服务，要么换端口：
sudo systemctl stop 旧服务

坑：有时候"占用者"是你没停干净的旧进程（ps aux 里找找），kill 它。

案例 8：Permission denied（权限拒绝）

三步问：

ls -l 文件                  # ① 谁是主人？权限是什么？
whoami                      # ② 你是谁？
sudo -u www-data ls 文件    # ③ 服务以什么身份运行时能不能访问？

高频剧情：Nginx 以 www-data 运行，网站根目录被 sudo 创建成了 root:root 且 700 权限 → 403 Forbidden。

sudo chown -R www-data:www-data /var/www/mysite   # 修复
sudo chmod -R 755 /var/www/mysite

另一个经典：SELinux（CentOS 系）开着，文件权限全对但就是 403——sudo ausearch -m avc -ts recent 查有无拦截，sudo setenforce 0 临时关验证。

案例 9：域名解析失败（unknown host）

ping 8.8.8.8              # ① IP 通吗？（通 → 说明纯 DNS 问题）
dig 域名 @8.8.8.8         # ② 公共 DNS 能查到吗？
cat /etc/resolv.conf      # ③ 本机用的 DNS 是谁？
systemctl status systemd-resolved   # ④ 本地解析服务正常吗？
# 若本机 DNS 是 127.0.0.53（systemd-resolved）：
resolvectl status          # 看实际配置

案例 10：证书过期（网站突然全警告）

现象：昨天还好好的，今天所有用户都看到"证书过期"。

echo | openssl s_client -connect 域名:443 2>/dev/null | openssl x509 -noout -dates
# notAfter 是昨天 → 实锤
# 解决：certbot renew（并检查自动续期的 timer）
sudo certbot renew && sudo systemctl reload nginx
systemctl list-timers | grep certbot    # 确认自动续期任务活着

案例 11：数据库连不上

systemctl status mysql         # ① 数据库活着吗
ss -tlnp | grep 3306           # ② 3306 端口在听吗
mysql -u 用户 -p -h 数据库IP    # ③ 手动连一次，看报什么错
# 常见错误对照：
# "Access denied" → 密码/账号/主机权限问题（用户表里的 'user'@'主机' 不匹配）
# "Can't connect" → 网络/防火墙/端口问题
# "Too many connections" → 连接数满了（调 max_connections 或查连接泄漏）

案例 12：防火墙拦了但你看不见（iptables 幽灵规则）

现象：服务正常、端口在听、本地 curl 通，但外部访问超时。

sudo iptables -L -n -v | head -30    # 看有没有 DROP 规则
sudo nft list ruleset | head -30     # 新版系统看 nftables
sudo ufw status verbose              # ufw 状态

别忘了云安全组（云服务器第二道门，案例里 50% 的"外部访问不通"都是它）。

案例 13：时间不对引发的血案

现象：证书莫名报错、程序日志时间错乱、集群间认证失败。

date                     # 看时间对不对（时区、快慢）
timedatectl status       # 详细时间状态
sudo timedatectl set-timezone Asia/Shanghai    # 改时区
# 时间同步：
sudo apt install -y chrony   # 或 systemd-timesyncd
sudo systemctl restart chrony
chronyc sources -v           # 看同步状态（^* 表示同步上了）

冷知识：时间偏差超过证书有效窗口、超过 Kerberos 的 5 分钟容差（Windows 域环境!）都会引发"莫名其妙"的故障。排障时"时间对不对"要进你的 checklist。

案例 14：配置改错了导致的雪崩

现象：reload 完配置，网站 502。

sudo nginx -t                   # 先验证（你改配置前验证了吗？）
tail -50 /var/log/nginx/error.log
# 对策流程永远一样：回滚 → 验证 → 再研究
sudo cp /etc/nginx/nginx.conf.bak /etc/nginx/nginx.conf   # 回滚备份
sudo systemctl reload nginx

铁律：改任何配置前先备份（cp 文件 文件.bak），改完先验证语法再 reload。

案例 15：日志暴涨刷爆磁盘

ls -lhS /var/log | head           # 按大小排列找大户
journalctl --disk-usage           # journal 占用
# 发现某应用每秒写几万行错误日志：先停下应用/修 bug，再清日志，再配 logrotate
# 看日志内容定位原因：
tail -100 /var/log/应用.log

案例 16：SSH 突然连不上

# 还能连上其他方式的话：
systemctl status ssh
ss -tlnp | grep :22
tail -50 /var/log/auth.log        # 看认证失败记录（被暴力破解？fail2ban 把你的 IP 封了？）
# 被 fail2ban 封了：sudo fail2ban-client status sshd / unban
# 完全连不上：云控制台 VNC 救援模式进系统检查

预防：改 sshd_config 时千万别关掉当前会话，先新开一个终端测试新连接成功了再关。

案例 17：磁盘 IO 100%（系统卡成幻灯片）

iostat -x 2                        # %util 高的设备就是它（需要 sysstat 包）
iotop                              # 看哪个进程在疯狂读写
# 常见元凶：数据库频繁落盘、日志狂写、备份任务、内存不足导致的 swap 抖动

案例 18：依赖服务连环倒塌（排障的终局思维）

现象：网站 502。查 Nginx 正常 → 查后端服务 normal → 但它连不上数据库。

# 顺着依赖链一路查下去：
curl -v http://localhost          # Nginx → 后端：502（后端无响应）
ss -tlnp | grep 8000              # 后端在听
tail app.log                      # 后端日志：无法连接数据库
systemctl status mysql            # 数据库死了，OOM 被杀了（回到案例4）

思维升级：现代系统是链条。排障不是查一个点，而是沿着调用链走：用户→LB→Web→App→DB→存储。哪一环断了，现象就会传上来。

7.4 比赛排障攻略（Module D 专项）

世界赛排障模块的模式：给你一台（或几台）预埋了故障的系统 + 一个工单列表（"张三说打印机用不了""网站间歇性 500"…），限时找出并修复。

训练方法：

  1. 找同学/队友互相"埋雷"：故意改错配置让对方修（最有效的训练！）
  2. 每学会一个新服务（nginx/mysql/dns），故意搞坏它 5 次再修好
  3. 收集自己的"维修记录本"：每次修的什么、怎么发现的、怎么修的——考前翻这本笔记就够了
  4. 熟悉本资料包 github-repos/ws2024-t39-module-d-main/（真实世界赛排障模块的环境构建和答案，含 CML 拓扑）

现场策略：

  • 先通读全部工单，按"确定性"排序（一眼能看出问题的先修）
  • 修一个，验证一个，不要同时改多处（改乱了连原来什么问题都忘了）
  • 卡住超过 10 分钟就跳过，换个工单修——比赛是按修复数量给分的，不是按难度
